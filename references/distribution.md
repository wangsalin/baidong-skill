# 白洞 · 分发与写回工作台

每期默认交付中文横版、中文竖版、英文横版、英文竖版，除非用户明确缩小本次范围。逐版列出成片、同名字幕、实际时长和验收状态；额外切片不计入这四版。竖屏直接讲原理，也要有完整例子、边界和结尾。

**单期文件铁律**：正式目录、四版工程、视频、字幕和封面命名统一按 `production.md` 第2节，沿用以往单期组织方式。直接交付单期根目录及文件；审阅网页只能辅助，不能替代 MP4 或以多层制作轮次目录作为正式交付。

## 1. 封面（四种尺寸）

出封面前先读 `covers.md`，查看随包 `assets/examples/cover-styles/contact-sheet.png` 与 `assets/examples/cover-v5/` 的原生竖版总览、四比例实例及设计索引。A 深蓝边界制止、B 朱红言语冲突、C 蓝色行动离开作为画法和配色参考；每期从正文实际冲突设计独立画面，不轮换三套构图，不把示例标题、丁叔和反问姐固定到所有选题。

按 `visual.md` 与 `covers.md` 选本期矛盾最清楚的一瞬间。短标题、人物反应与背景空间共同说明问题；标题用粗黑体大字，关键词可用黄、白或蓝，按背景对比选择，不强制旧的黑字蓝词亮底。封面沿用角色身份和画法，不连带改变正片的色彩、字体和字幕版式。

在本期 `cover.js` 实际实现场景、标题排版与人物动作，按四种比例分别构图。模板旧底稿不会自动生成这三种风格：只改 `COVER` 的 `bg` / `pop`，或新增未被读取的 `style`、道具字段，都不算完成新风格。`story.js` 的 `COVER` 保留本期标题、强调词与已有角色设置的接线；只使用当前渲染代码真正支持的字段。

完成绘制、字体和四尺寸适配后，在 WSL 中从实际 Skill 根目录执行：

```sh
sh "$BAIDONG_SKILL_ROOT/scripts/cover.sh" /path/to/episode
```

生成器在各语言工程得到 `cover-4x3.jpg`（B 站，1440×1080）、`cover-16x9.jpg`（横版，1920×1080）、`cover-3x4.jpg`（小红书等，1080×1440）、`cover-9x16.jpg`（竖版，1080×1920）。根目录正式交付使用 `cover-zh-*.jpg` 和 `cover-en-*.jpg`，按 `production.md` 核对对应原图。逐张检查完整图和缩略图：标题、表情、手势与识别配饰清楚，气泡话语归属正确，没有意外裁切或遮挡；不能将横版机械拉伸或直接裁切作为竖版交付。

英文发布使用对应英文标题和画面文字，独立改写、断行和检查遮挡；可对照随包第 13 期英文四比例实例。按 `covers.md` 记录观众疑问与正文依据，核对标题承诺、人物动作和正文兑现一致。9:16 与 3:4 分别构图并做手机检查；含竖版的审阅页默认展示 9:16，逐一验证比例切换、图片链接和已有对比功能。随包三风格参考与 V5 案例均不是本期输出，也不代表平台点击率已验证。

## 2. 竖屏成片

默认竖屏为可独立观看的缩减版，通常 30–60 秒、尽量不超过一分钟；保留共鸣细节、完整因果和答案。长竖屏仅在用户本次明确要求时制作。所有竖屏都使用原生 9:16 画面。中文版和英文版共用第九期的版面逻辑，具体字幕断行、字号和文本密度按语言调整；背景色按每期主题选，不固定黄底或玫红底。制作、渲染、安全区和画面验收统一按 `vertical.md` 执行。

竖屏开头直接点出问题或机制，主体通过完整场景与全屏解释图交替推进，结尾讲完原理、边界和结论。不要把横版缩成小窗口放在底部，也不要让底部文字挡住主要画面。原理短片可以从横版选取完整段落，但首句、解释和结尾都必须完整；找不到合适段落时，写竖屏专用稿并重做对应画面。

`scripts/clip.sh` 是旧式横版画面包装工具，不用于制作本规则下的原生竖屏版；只有用户明确指定旧包装或横版小窗效果时才调用。默认缩减版与另行要求的长竖屏分别记录时长、字幕和验收结果。

## 5. 写回工作台

工作台：https://claude.ai/artifact/HTrkjS7mwrQUg4Nz9nB2ck ，数据在它的共享数据库里，用 `ArtifactData` 工具读写（不是 Artifact 发布）。

**先读后写**：`ArtifactData` `get`（`collection: "episodes"`，`doc_id: "ep01"` 这样的 id）拿到当前 `version`，写的时候带上 `if_version`。多个字段一次写完，用 `update`（合并字段），不要用 `set`（会整条覆盖，用户在工作台里填的东西会丢）。用户可能在工作台里改过内容，读到的内容以工作台为准，不要用本地旧稿覆盖。

本期还没有记录时：先 `list` 一下 `episodes` 看已有的 id 和期号格式，再新建（`set`，不带 `if_version`），同时在 `topics` 里把对应选题的 `status` 改成“已立项”。

**集合**：`topics`（选题库）、`episodes`（每期）、`metrics`（数据复盘）、`knowledge`（运营知识库）、`benchmarks`（对标账号）；设置在 `config/settings`、账号设定在 `config/profile`。

**`episodes` 记录的字段**（写回时用这些名字）：

| 字段 | 内容 |
|---|---|
| `no`、`title`、`topicId`、`buckets` | 期号、标题、对应选题 id、关系桶数组（如 `[4]`） |
| `angle`、`analysis`、`mechanism`、`action`、`pitfalls`、`commentQ` | 切口、选题分析、主机制、小动作、要避开的坑、评论区问题 |
| `hooks` | `{h1: {type, text, note, o}, h2: …, h3: …}`，`chosenHook: "h1"` |
| `seg` | `{s1: {title, text}, …, s6: {title, text}}`：六段的标题和台词 |
| `check` | 留存自查清单，`{键: true/false}` |
| `facts` | `{f1: {o, claim, url}, …}` |
| `coverText`、`coverHighlight` | 封面大字（用 `/` 分行）、强调关键词；颜色按 `covers.md`，不新增数据库字段 |
| `covers` | `{"16x9": {path}, "4x3": {path}, "3x4": {path}, "9x16": {path}}`，path 写本地路径 |
| `prod` | `{step, stuck, stuckNote, note, paths}`。`step` 是步骤序号：0 脚本、1 配音、2 关键镜头确认、3 成片、4 封面、5 竖版切片；`paths` 是 `{p0: 脚本路径, p1: 配音目录, …, p3: 成片路径, p5: 切片路径}` |
| `mat` | `{douyin: {title, desc, tags}, xhs: {…}, bili: {…}, sph: {…}, ks: {…}, yt: {…}}` |
| `chapters` | `{bili: "00:00 …\n…", yt: "…"}` |
| `xhsCards` | `{c1: {o, head, body}, …}`，6 张 |
| `pub` | 发布状态，`{平台: {status, time, url}}`。由用户发布后自己填，skill 不要写 |
| `review` | `{conclusion, comments}`；指标与评论来自用户录入，skill 可据此整理结论，保留用户已有内容 |

### 发布后复盘与回流

只使用用户手动录入的 `metrics` 和工作台评论，不抓取平台数据。分平台判断，并尽量比较相同发布后时长的数据；不把不同平台的播放量或留存率直接横向比较。现有指标为 `views`、`r3`、`completion`、`avgDur`、`comments`、`saves`、`shares`、`follows`，不要推断未记录的封面点击率。工作台基线是同平台已有数据的前 3–5 期均值，样本不足 3 期时标明“基线未建立”。工作台将基线 ±10% 以内视为正常波动，这只是显示口径，不能证明统计显著性或因果。全平台汇总可看总量，但不能替代分平台诊断。

把观察、解释和下一步动作写进已有 `review.conclusion`，不新增字段：

- 分平台记录关键指标相对各自基线的变化，并注明样本量不足或数据缺失。
- 找到最明显的信号：3 秒留存偏低时检查开场对象、钩子与封面承诺是否一致；完播率或平均时长偏低时回看内容推进；评论偏少时检查内容是否引出具体经历、评论问题是否好回答。只有用户提供留存曲线或掉点时间时，才定位到具体段落；仅凭平均时长不能确定 s4 就是问题。评论、收藏、分享和涨粉结合播放量看比例，不单独用数量推断原因。
- 从评论里摘录能代表疑问、反驳或亲身经历的原话，附点赞数（若有），写入 `review.comments`；将有明确延展价值的评论转成选题，关联 `topicId`。不只按点赞数挑评论。
- 只定一个下一期可验证的改动，例如钩子更具体或 s4 先给案例；避免一次改很多处后无法判断效果。

结论要区分数据事实和推测，不把一次波动当作因果证明。可简写为：`数据：……；最大信号：……；可能原因：……（待验证）；评论需求：……；下期只改：……；验证指标：……`。把确认过的通用经验整理进 `knowledge`，新需求回到 `topics`，下一期选题分析参考这些记录。

如果工作台以后加了新字段（比如本期出场角色），先读一条现有记录看清结构再写，不要猜字段名。

**什么时候写**：
- 第一段（脚本）结束：`analysis` 到 `commentQ`、`hooks`、`chosenHook`、`seg`、`check`、`facts`、`coverText`、`coverHighlight`，`prod.step = 0`。
- 成片后：`prod.step = 3`，`prod.paths.p3`。
- 分发后：`covers`、`mat`、`chapters`、`xhsCards`，`prod.step = 5`，`prod.paths.p5`。

四版的路径、完成状态和未完成原因写入已有 `prod.note` 并关联本地交付清单；不新增数据库字段，不改写 `pub` 或 `review`。四版未齐时，不把本期标为全部完成；工具不可用时保留本地候选并明确未同步。
